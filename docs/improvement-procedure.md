# 呼吸タイマー 改善実装・検証手順書

作成日: 2026-09-08  
対応仕様: [改善要件定義書](improvement-requirements.md)  
本書は今後行う修正の手順であり、実装修正・検証の完了報告ではない。

## 1. 着手前の確認

1. `git status --short` で既存変更を確認する。変更を破棄しない。
2. GitHubへ接続できる環境で `git fetch origin` を行い、レビュー対象 `51365dc` と最新コードの差を確認する。差があれば要件の対象箇所を更新する。
3. 作業ブランチを作成する。例: `git switch -c codex/improve-breathing-timer`。
4. `java -version` と `./gradlew --version` を確認する。Windowsは `.\gradlew.bat --version` を使用する。
5. Gradleキャッシュへ書き込めない場合は、書き込み可能なキャッシュ場所を使う。例: `.\gradlew.bat -g "$env:TEMP\breathing-gradle-cache" --version`。以降も同じ `-g` を指定する。初回は依存物のダウンロードにネットワークが必要。
6. 現状の起動・テスト結果を記録する。個人用DBから独立した検証用PostgreSQLを用意する。

## 2. 入力検証を修正する（R-01）

1. `BreathingRecordForm` を作成し、4項目をInteger型で定義する。要件表の `@NotNull`、`@Min`、`@Max` を付ける。
2. GET `/breathing/new` でフォームDTOをモデルへ登録する。モデル名は例えば `recordForm` に統一する。
3. POSTを `@Valid @ModelAttribute("recordForm") BreathingRecordForm form, BindingResult result` で受ける。`BindingResult` は対象引数の直後に置く。
4. `result.hasErrors()` の場合は保存せず `breathing/form` を返す。型変換エラーの日本語メッセージを `messages.properties` に定義する。
5. 正常時だけDTOから新しいEntityへ値をコピーする。Serviceが保存したEntityを返すようにし、そのIDでリダイレクトする。
6. フォームへ `th:object`、各項目へ `th:field` と `th:errors` を設定する。HTML制約とラベルの関連付けを追加する。
7. Controllerテストで境界値・範囲外・未入力・文字列・小数・巨大な整数を送信する。不正時にServiceの保存が呼ばれないことも確認する。

注意: Entityに直接 `@Valid` を付けるだけの修正にしない。保存前にはサーバー管理の `createdAt` が未設定であり、その制約まで入力エラーになるため。

## 3. タイマー処理を整理する（R-02〜R-04）

1. テンプレートに設定値の受け渡しだけを残し、時間計算・状態遷移を `static/js/` へ分離する。DOM描画と時計を差し替え可能にする。
2. 状態を準備・実行中・一時停止・完了の4種類にする。状態更新時にボタン表示を一括更新する。
3. 初期化時に0秒フェーズを実行対象から除外する。総時間も有効フェーズの合計から求める。
4. 実行開始時に時計の基準値と累積経過ミリ秒を保持する。更新ごとに経過時間からサイクルとフェーズ、残り時間を算出する。
5. 更新が遅れた場合は、実際の経過位置まで進める。最終時刻を超えていれば完了にする。音は更新1回につき最大1回とする。
6. 一時停止では最新時刻まで経過時間を反映して保持する。再開では新しい基準時刻を設定する。円も同じ進捗値から描画する。
7. `visibilitychange` で非表示になった際は実行中のみ停止する。表示に戻っても自動再開しない。
8. リセットで更新予約を解除し、経過時間・円・フェーズ表示を初期化する。完了後の再実行も初期状態から始める。
9. 重複したinterval処理と `return` 後の到達不能コードを除去する。
10. 模擬時計を使う自動テストを用意する。実際の秒数だけ待つテストにはしない。Node.jsの標準テストランナー等、採用した実行環境とコマンドをREADMEへ記載する。

## 4. DB初期化を再現可能にする（R-05）

### 4.1 新規DB

1. 使用中のSpring BootでのFlyway設定とPostgreSQL用依存関係を公式ドキュメントで確認し、`build.gradle` へ追加する。
2. `src/main/resources/db/migration/V1__create_breathing_records.sql` を作成する。
3. Entityと対応する以下の列を定義する。

| 列 | PostgreSQL型・制約 |
| --- | --- |
| id | BIGINT、自動採番、PRIMARY KEY |
| inhale_seconds | INTEGER、NOT NULL、1〜30 |
| hold_seconds | INTEGER、NOT NULL、0〜30 |
| exhale_seconds | INTEGER、NOT NULL、1〜30 |
| cycle_count | INTEGER、NOT NULL、1〜20 |
| created_at | TIMESTAMP WITHOUT TIME ZONE、NOT NULL |

4. `spring.jpa.hibernate.ddl-auto=validate` とする。サンプル設定も合わせる。
5. 空の検証用DBで起動し、マイグレーション履歴とテーブルを確認する。
6. 1件登録して再起動し、重複作成がなくデータが保持されることを確認する。

### 4.2 既存DB

1. 接続先を確認し、バックアップを取得する。まず復元した検証用DBで作業する。
2. 列型、NOT NULL、自動採番、制約、保存済み値をV1と比較する。
3. 差分や不正値があれば対応を決める。データ削除で解決せず、修正・退避などの扱いを記録する。
4. V1相当の状態へ整合させてから、その既存DBだけにバージョン1の明示的ベースラインを設定する。具体的なコマンドは採用したFlywayの実行方法に合わせてREADMEへ残す。
5. 共通設定で `baseline-on-migrate` を無条件に有効化しない。以後の変更はV2以降に追加し、適用済みV1を書き換えない。
6. 起動・保存・再起動・既存件数保持を確認した後、実DBへの適用手順を確定する。

## 5. 起動説明とテスト環境を整える（R-05〜R-06）

1. READMEへJDK 25、PostgreSQL、必要ならNode.js・Dockerの前提を記載する。
2. 開発用DB・ユーザーの作成と権限、サンプル設定のコピー、接続情報の編集、localプロファイルでの起動を記載する。
3. POSIXの `./gradlew bootRun` とWindowsの `.\gradlew.bat bootRun` を併記する。
4. テスト専用プロファイルを用意する。通常のlocal設定や個人用DBへ依存させない。
5. PostgreSQLの統合テスト環境を固定する。Testcontainers採用時はコンテナから接続情報を注入し、DDLと保存を検証する。
6. Javaテストは `./gradlew test`（Windows: `.\gradlew.bat test`）で実行する。JavaScriptの確定したテストコマンドもREADMEに記載する。
7. READMEの「今後の拡張予定」と現在の機能が一致するように更新する。設定保存と実施履歴を区別する。

## 6. 追加改善を行う場合（R-07〜R-09）

1. フォームと一覧にviewport・langを設定し、狭い画面の余白を調整する。一覧表だけを横スクロール可能にする。
2. 円の最大拡大後サイズが画面幅を超えないよう調整する。
3. 一覧取得に作成日時降順、ID降順のソートを指定し、0件の案内を追加する。
4. 音の切り替えボタンを追加し、選択状態と読み上げ用の状態を更新する。再生失敗はタイマー処理を中断させない。

## 8. 外部公開する場合（R-10）

1. 利用者・記録の公開範囲・認証方式を決定して追加設計する。
2. 個人記録として扱う場合は、所有者との紐付け、既存データの扱い、一覧とID指定取得の権限確認を実装する。
3. CSRFを有効化し、フォームの正規POST成功とトークンなしPOST拒否を検証する。
4. 未認証アクセスと他ユーザーのIDを指定したアクセスが拒否されることを検証する。
5. 公開設定で開発用の全件許可が残っていないことを確認する。
